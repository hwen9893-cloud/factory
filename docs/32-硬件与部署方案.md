# 1. 内存与存储升级（到手优先事项）

## 1.1 升级优先级

| 优先级 | 项目 | 现状 → 目标 | 理由 |
|--------|------|------------|------|
| **P0** | 内存 | 64GB → **128GB（256GB 更佳）** | 视频扩散 + LLM 同机运行，RAM 决定能否并行与 CPU offload |
| **P1** | NVMe 扩容 | 2TB → 再加 **1×2~4TB PCIe4** | 一块专放模型权重，一块做视频 scratch |
| **P2** | 散热压测 | 原厂风冷 | 5090 + 285K 满载噪音/降频实测 |
| **P3** | 备份盘 | 4TB HDD 保留 | 仅冷归档 + 本地备份，不进热路径 |

## 1.2 内存为什么是最大短板

单卡运行时系统内存承担三件事：① 模型换入换出缓冲（LLM/图/视频模型切换经过 RAM）；② CPU offload（显存放不下的层临时挪到 RAM，视频模型尤甚）；③ 视频中间帧/解码缓存/FFmpeg 管线缓冲。

> 64GB 在「一边挂写作 LLM、一边跑视频」时极易吃满触发 swap，拖垮吞吐。**128GB 是舒适下限，256GB 可让写作模型常驻 + 视频模型并行更从容。**

## 1.3 存储分层

```text
NVMe #1（系统盘 2TB）
  ├─ Ubuntu / 环境 / Docker
  └─ 常用大模型权重（LLM + 视频模型，热加载）
NVMe #2（新增 2~4TB）
  └─ 视频 scratch：关键帧、分段视频、插帧/超分中间产物（高 IO、可清理）
4TB HDD（5400 转）
  └─ 冷归档：成片母带、历史素材、数据库全量备份（顺序读写为主）
NAS / 移动硬盘（异地）
  └─ 知识库 + 成功/失败案例库 + LoRA 权重
```

> 规则：**热数据（模型、scratch）永远在 NVMe，HDD 只做归档与备份。**

# 3. VRAM 预算（32GB 单卡是硬约束）

| 任务 | 显存占用 | 单卡可行性 | 建议 |
|------|---------|-----------|------|
| LLM 写作（14B 4-bit） | 10~14GB | ✅ 流畅 | 白天常驻，日常主力 |
| LLM 写作（32B 4-bit） | 20~24GB | ✅ 可行 | 追求质量时用，与其它任务错峰 |
| Embedding / 检索 | 1~3GB | ✅ | 可与 LLM 共存 |
| 图像生成 SDXL/Flux | 8~16GB | ✅ | 关键帧、角色图、场景图 |
| **视频生成（Wan/Hunyuan/LTX）** | **24~32GB＋** | ⚠️ 紧张 | **需独占显存**，控分辨率/帧数/时长，必要时 CPU offload |
| LoRA 微调 | 16~24GB | ✅（小批量） | 夜间/周末单独跑 |
| TTS / 音效 | 2~6GB | ✅ | 与视频错峰 |

> **核心结论：视频生成基本独占整张卡。** 这印证了「文字每日、动画按周集中」的正确性——写作与视频不在同一时刻抢显存。

# 4. 单卡工作流（时段错峰）

## 4.1 单卡三条铁律

```text
1. 一个时间段只常驻一种「重模型」，避免频繁换入换出（换模型 = 几十秒~几分钟 IO 浪费）
2. 视频生成独占显存，跑视频时不并行大 LLM
3. 用任务队列（Redis/Celery）把 GPU 喂满，失败镜头自动重试、降规格重试
```

## 4.2 一天内 GPU 时段划分

| 时段 | 常驻模型 | 主要任务 | 显存策略 |
|------|---------|---------|---------|
| 白天（人机协作） | 写作 LLM（14~32B） | 写正文、分镜脚本、Prompt、记忆更新、轻量出图 | LLM 常驻，SDXL 按需短时占用 |
| 夜间（无人值守） | 视频模型常驻 | 批量图生视频、插帧、超分、后处理 | 视频模型独占，队列跑满 |
| 周末（集中收尾） | 视频 + 音频交替 | 集中剪辑、TTS 配音、混音、渲染、质检 | 分阶段切换，避免同时抢卡 |

## 4.3 每集 20 分钟镜头分级（GPU 只投给动态镜头）

```text
20 分钟 / 集
├── 3 分钟  S 级关键动态   → 高规格视频生成（多次重试挑最优）
├── 5 分钟  A 级普通动态   → 标准规格视频生成
├── 5 分钟  首尾帧动画     → 关键帧 + 图生视频/插帧，省算力
├── 4 分钟  静态运镜 / 2.5D → 单图 + 运镜脚本，几乎不吃视频模型
├── 2 分钟  对话复用镜头   → 资产复用 + 口型驱动
└── 1 分钟  环境/转场/特效  → 素材库 + 后期
```

> 两集共 40 分钟，真正吃 GPU 的「S+A 级动态」约 16 分钟——其余靠首尾帧、静态运镜、复用完成，**这是单卡能长期跑通的关键**。

## 4.4 失败与降级策略

```text
镜头生成失败
  → 自动重试（换 seed）
  → 仍失败：降规格（降分辨率/帧数）重试
  → 再失败：转「首尾帧 + 插帧」兜底
  → 记录进「视频失败案例记忆」，供下次 Prompt 规避
```

# 5. 部署拓扑（Docker，全本地）

```
本地工作站（Ubuntu / RTX 5090 32GB）
 ├─ Docker: infra（Redis/Celery/Nginx/MinIO/监控）
 ├─ Ollama / vLLM（center.model LLM 后端）
 ├─ ComfyUI（center.model 图像/视频后端，占 GPU）
 ├─ 本地 TTS（XTTS/CosyVoice/Piper）
 ├─ PostgreSQL + pgvector（center.knowledge / lineage / 向量检索）
 ├─ GPU 队列调度器（Redis/Celery，见 §7）
 └─ orchestrator + factories（novel/visual/animation/audio）+ centers
        │  （可选溢出）
        ▼
云 GPU（仅在本地队列积压超阈值时按需租用，非默认路径）
```

- `infra` 的容器、队列、存储、监控、备份全部本地。
- **视觉/视频/LoRA 默认本地夜间批处理**；云 GPU 仅作产能溢出的可选兜底（见 `23`）。

# 7. 单卡资源竞争与 GPU 队列调度（新核心组件）

> Mac + 云时代不存在、本地单卡时代必须解决：**一张 32GB 卡是写作/视频/TTS/LoRA 的共享瓶颈。**

```text
单张 32GB 显卡 = 写作 / 视频 / TTS / LoRA 的共享瓶颈
        │
        ▼
必须新建：GPU 队列调度 + 模型常驻策略
（Redis/Celery 队列 + 显存预算表 + 单任务独占 + 失败降级重试）
```

调度器职责（实现契约见 `62` §10）：

| 能力 | 说明 |
|------|------|
| 显存预算表 | 按 §3 表登记每类任务的显存占用，防止超额并发 |
| 单任务独占 | 视频/LoRA 任务申请「GPU 独占锁」，期间不调度大 LLM |
| 模型常驻策略 | 按时段（§4.2）决定常驻哪种重模型，减少换入换出 |
| 失败降级 | 按 §4.4 自动重试→降规格→兜底 |
| 优先级队列 | 白天写作高优先（人在环），夜间视频批处理低优先 |

# 9. 备份、监控与灾备预案

## 9.1 备份策略

| 数据 | 频率 | 存储位置 | 保留期 |
|------|------|---------|--------|
| PostgreSQL（知识库/lineage/向量） | 每日增量 + 每周全量 | NAS + 异地云存储 | 90 天 |
| 资产文件（图/音/视频成品） | 新产物即时同步 | NAS（主）+ 云对象存储（副） | 永久 |
| **LoRA 权重 + 成功/失败案例库** | 训练后即时 | NAS + 异地 | 永久（重训成本高，重点保护） |
| 模型权重（GGUF/ComfyUI） | 拉取后本地固化 | NVMe + NAS | 永久 |
| Docker 配置/compose | 随代码提交 Git | GitHub | — |

## 9.2 监控指标

- 服务存活（orchestrator/PostgreSQL/Ollama/ComfyUI/Redis/Celery）：健康检查每 60 秒
- **GPU 利用率/显存/温度**：`nvidia-smi` 采样，温度 > 83℃ 或持续降频告警
- 队列积压：Celery 队列长度 > 50 告警
- 流水线成功率：对接 `22` 标准 #5、`72` §2.3
- 磁盘用量：NVMe > 80% 告警（视频 scratch 增长快）
- 稳定性目标：核心服务 **≥ 30 天无人工重启**

## 9.3 灾备预案（本地工作站单点故障）

> 本地工作站承载全部 infra + GPU 生产，是唯一物理节点（单点故障）。相较 Mac 时代，**单点风险更高**（本地也是唯一算力），异地备份权重加大。

**RTO ≤ 4 小时**（Phase 1 接受；规模化后收紧到 ≤ 1 小时）；**RPO ≤ 24 小时**（靠每日备份）。

| 故障场景 | 恢复步骤 | 预期时长 |
|---------|---------|---------|
| 服务崩溃（非硬件） | `docker compose restart` | < 10 min |
| 系统崩溃（可重启） | 重启 → docker compose up -d → 验证服务 | < 30 min |
| GPU 故障（需送修/换卡） | ① 写作/知识库/评测在 CPU 上降级运行；② 视觉/视频任务暂停排队；③ 换卡后恢复 | 视保修而定 |
| 整机硬件故障 | ① 从 NAS 恢复 PostgreSQL；② 临时借用笔记本/云主机起最小写作服务；③ 修复后迁回 | 2–4 h |
| NAS 同时故障 | 从异地云存储恢复最近一次全量备份 | 4–8 h（极低概率） |

## 9.4 恢复演练（每季度一次）

- 从 NAS 备份恢复 PostgreSQL 到测试实例，验证数据完整性
- 确认 Docker compose 从 Git 可一键拉起全部服务
- 验证 LoRA 权重与案例库可从异地恢复
- 记录实际耗时，超 RTO 则优化脚本

> **恢复脚本**放在 `scripts/disaster_recovery/`，含 `restore_db.sh` / `start_services.sh`，可在无文档情况下独立执行。

# 10. 到手核对清单（Ubuntu）

```bash
lscpu | grep -E "Model name|CPU\(s\)|Thread"                       # CPU 核心/线程
sudo dmidecode -t baseboard | grep -E "Manufacturer|Product"      # 主板芯片组
sudo dmidecode -t memory | grep -E "Size|Speed|Type|Rank"         # 内存通道/频率
nvidia-smi -q | grep -E "Product Name|VBIOS|Total|Power Limit"     # 5090 真伪与显存
lsblk -o NAME,SIZE,MODEL,ROTA                                      # NVMe 型号/容量
```

- [ ] 内存型号与 W880 主板匹配（UDIMM DDR5，双通道）
- [ ] 5090 真卡验证：`nvidia-smi` 显示 32GB、功耗墙正常、VBIOS 非篡改
- [ ] 电源 12VHPWR 接口到位，5090 供电线原装
- [ ] 满载 30 分钟压测：GPU 温度 < 83℃、无明显降频、噪音可接受
- [ ] NVMe 实测顺序读写 ≥ 5GB/s（PCIe 4.0 达标）
