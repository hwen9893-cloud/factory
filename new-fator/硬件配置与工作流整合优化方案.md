## 0. 结论速览（TL;DR）

| 维度 | 现状判断 | 一句话结论 |
|------|---------|-----------|
| GPU | RTX 5090 32GB ✅ | 单卡能扛这个目标，是全机的算力核心 |
| CPU/主板 | Core Ultra 9 285K + W880 ✅ | LGA1851 平台，兼容确认，24核32线程无问题 |
| 内存 | 64GB ⚠️ | **最大短板**，视频生成 + LLM 同机时会成瓶颈，建议 128GB 起步 |
| 存储 | 2TB NVMe + 4TB 5400 HDD ⚠️ | NVMe 偏小、HDD 太慢，需重做分层 |
| 工作流 | 每周集中做动画 ✅ | 方向正确，需按「单卡队列 + 模型常驻」进一步细化 |

> 一句话：**CPU/主板/显卡组合已经选对，现在要做的是把内存补到 128GB+、存储做好 NVMe 分层**，然后用「白天写作、夜间跑视频、周末剪辑」的单卡队列工作流落地即可。

### 1.1 到手核对命令（Ubuntu）

```bash
# CPU 真实型号与核心/线程

# 主板/芯片组真实型号
```

## 2. 硬件配置优化建议

### 2.1 升级优先级（按性价比排序）

| 优先级 | 项目 | 现状 → 目标 | 理由 |
|--------|------|------------|------|
| P0 | **内存** | 64GB → **128GB（256GB 更佳）** | 视频扩散 + LLM 同机运行，系统 RAM 直接决定能否并行、能否用大 offload |
| P1 | **NVMe 扩容** | 2TB → **再加 1×2~4TB PCIe 4.0** | 一块专放模型权重，一块做视频 scratch |
| P2 | **散热压测** | 原厂风冷 | 满载噪音/降频实测，必要时改分体或加机箱风道 |
| P3 | **备份盘** | 4TB HDD 保留 | 只当冷归档 + 本地备份，不进热路径 |

### 2.2 内存为什么是最大短板

单卡跑本方案时，系统内存承担三件事：
1. **模型换入换出的缓冲**（LLM 权重、SDXL/Flux、视频模型在切换时经过 RAM）；
2. **CPU offload**：显存放不下的层临时挪到 RAM（视频模型尤其需要）；
3. **视频中间帧 / 解码缓存 / FFmpeg 管线缓冲**。

> 64GB 在「一边挂着写作 LLM、一边跑视频」时非常容易吃满并触发 swap，直接拖垮吞吐。**128GB 是舒适下限，256GB 可让写作模型常驻 + 视频模型并行更从容。**

### 2.3 存储分层方案

```text
NVMe #1 (系统盘 2TB)
  ├─ Ubuntu / 环境 / Docker
  └─ 常用大模型权重（LLM + 视频模型，热加载）

NVMe #2 (新增 2~4TB，建议)
  └─ 视频 scratch：关键帧、分段视频、插帧/超分中间产物（高 IO、可清理）

4TB HDD (5400 转)
  └─ 冷归档：成片母带、历史素材、数据库全量备份（顺序读写为主）

（可选）NAS / 移动硬盘
  └─ 异地备份：知识库 + 成功/失败案例库 + LoRA 权重
```

规则：**热数据（模型、scratch）永远在 NVMe，HDD 只做归档与备份**。

### 2.4 稳定性核对清单

- [ ] 内存型号与 W880 主板匹配（UDIMM DDR5，双通道）
- [ ] 5090 真卡验证：`nvidia-smi` 显示 32GB、功耗墙正常、VBIOS 非篡改
- [ ] 电源单路 12V-2×6/12VHPWR 接口到位，5090 供电线原装
- [ ] 满载 30 分钟压测：GPU 温度 < 83℃、无明显降频、噪音可接受
- [ ] NVMe 实测顺序读写达标（PCIe 4.0 应 ≥ 5GB/s）

## 3. 这台机器能做什么 / 做不了什么（VRAM 预算）

RTX 5090 32GB 是**全流程的硬约束**。按显存把任务分档：

| 任务 | 显存占用（参考） | 单卡可行性 | 建议 |
|------|-----------------|-----------|------|
| LLM 写作（14B 4-bit） | 10~14GB | ✅ 流畅 | 白天常驻，日常主力 |
| LLM 写作（32B 4-bit） | 20~24GB | ✅ 可行 | 追求质量时用，注意与其它任务错峰 |
| Embedding / 检索 | 1~3GB | ✅ | 可与 LLM 共存 |
| 图像生成 SDXL/Flux | 8~16GB | ✅ | 关键帧、角色图、场景图 |
| **视频生成（Wan/Hunyuan/LTX）** | **24~32GB＋** | ⚠️ 紧张 | **需独占显存**，控制分辨率/帧数/时长，必要时 CPU offload |
| LoRA 微调 | 16~24GB | ✅（小批量） | 夜间/周末单独跑 |
| TTS / 音效 | 2~6GB | ✅ | 与视频错峰即可 |

**核心结论：视频生成基本要独占整张卡。** 这正好印证了原工作流「文字每日、动画按周集中」的正确性——不要指望写作和视频在同一时刻抢显存。

## 4. 工作流优化建议（结合单卡实际）

延续你原方案的 10 Agent 架构与每周节奏，这里补上**单卡落地要点**。

### 4.1 单卡三条铁律

```text
1. 一个时间段只常驻一种「重模型」，避免频繁换入换出（换模型 = 几十秒~几分钟 IO 浪费）
2. 视频生成独占显存，跑视频时不并行大 LLM
3. 用任务队列（Redis/Celery）把 GPU 喂满，失败镜头自动重试、降规格重试
```

### 4.2 一天内的 GPU 时段划分

| 时段 | 常驻模型 | 主要任务 | 显存策略 |
|------|---------|---------|---------|
| 白天（人机协作） | 写作 LLM（14~32B） | 写正文、分镜脚本、Prompt、记忆更新、轻量出图 | LLM 常驻，SDXL 按需短时占用 |
| 夜间（无人值守） | 视频模型常驻 | 批量图生视频、插帧、超分、后处理 | 视频模型独占，队列跑满 |
| 周末（集中收尾） | 视频 + 音频交替 | 集中剪辑、TTS 配音、混音、渲染、质检 | 分阶段切换，避免同时抢卡 |

### 4.3 每周排程（在你原表上叠加 GPU 预算）

| 天 | 文字（白天，LLM 常驻） | 动画/GPU（夜间批处理） |
|----|----------------------|----------------------|
| 周一 | 第 1、2 章 + 整理剧情状态 + 提取动画候选场景 | — |
| 周二 | 第 3、4 章 + 更新人物/伏笔/世界观 | — |
| 周三 | 第 5、6 章 + 确定本周第 1 集内容 | 出第 1 集角色/场景关键帧（SDXL/Flux） |
| 周四 | 第 7、8 章 + 第 1 集分镜/资产/关键帧 | 夜间：第 1 集 S/A 级动态镜头批量图生视频 |
| 周五 | 第 9、10 章 + 确定第 2 集内容 | 夜间：第 1 集剩余镜头 + 插帧/超分 |
| 周六 | 第 11、12 章 + 第 2 集分镜/素材 | 夜间：第 2 集视频素材 + 配音 TTS |
| 周日 | 第 13、14 章 | 两集剪辑、字幕、混音、质检、发布 |

### 4.4 每集 20 分钟的镜头分级（决定 GPU 花在哪）

沿用你的镜头结构，把 GPU 重算力**只投给动态镜头**：

```text
20 分钟 / 集
├── 3 分钟  S 级关键动态   → 高规格视频生成（多次重试挑最优）
├── 5 分钟  A 级普通动态   → 标准规格视频生成
├── 5 分钟  首尾帧动画     → 关键帧 + 图生视频/插帧，省算力
├── 4 分钟  静态运镜 / 2.5D → 单图 + 运镜脚本，几乎不吃视频模型
├── 2 分钟  对话复用镜头   → 资产复用 + 口型驱动
└── 1 分钟  环境/转场/特效  → 素材库 + 后期
```

> 两集共 40 分钟，真正吃 GPU 的「S+A 级动态」约 16 分钟，其余靠首尾帧、静态运镜、复用完成——**这是单卡能长期跑通的关键**。

### 4.5 失败与降级策略（保证队列不空转）

```text
镜头生成失败
  → 自动重试（换 seed）
  → 仍失败：降规格（降分辨率/帧数）重试
  → 再失败：转「首尾帧 + 插帧」兜底
  → 记录进「视频失败案例记忆」，供下次 Prompt 规避
```

## 5. 记忆系统与「越用越聪明」（结合本机落地）

保留你原方案的 7 层文字记忆 + 4 类动画视觉记忆，落地到本机：

- **数据库**：PostgreSQL + pgvector（本地，轻量、无需额外服务）——存世界观/人物/剧情/伏笔/文风/审美/失败记忆 + 角色视觉/场景视觉/镜头语言/视频失败案例。
- **角色视觉记忆**（关键，保证一致性）示例字段：`lora_id / face_ref / costume / weapon / voice_id / common_camera`。
- **数据积累**：每日「AI 原稿 vs 用户修改稿」的差异入库 → 每周总结文风/人物/剧情/失败镜头/用户偏好 → 每 20~30 万字做一次 LoRA/SFT 微调（夜间或周末单卡跑）。

> 硬件对应关系：**pgvector 检索几乎不占显存**，可与写作 LLM 常驻共存；**LoRA 微调放到夜间/周末**，与视频生成错峰。

## 8. 完成 RAM / NVMe 扩展后的项目调整

扩展硬件只是第一步。真正的影响是：**整个项目的地基假设变了。** 现有 `docs/` 文档体系（`21`/`24`/`32`/`33`）都建立在「**Mac Studio（MPS，不能跑 CUDA 视频/LoRA）+ 云 GPU 突发**」之上，并据此把视频和 LoRA 硬性推给云。现在有了本地 CUDA 5090，这条硬约束消失，需要连锁调整。

### 8.1 地基假设的变化（改哪些文档）

| 现有文档 / 假设 | 需要的调整 |
|----------------|-----------|
| `docs/32-硬件与部署方案`：Mac + 云突发；§3「MPS 不能做视频/LoRA」硬边界 | **改写为本地单卡 CUDA 工作站**；视频/LoRA 从「云突发」改为「本地夜间批处理」 |
| `docs/21-精益路线`：「Mac 最不擅长视频 → 全动画自然推后」 | 硬件理由不再成立，动画推后改由 **市场信号 + GPU 时间预算 + M3.5 一致性** 决定 |
| `docs/33-center.model` 只封装本地 LLM + 云 fallback | 把 **ComfyUI（图/视频）、本地 TTS** 提升为一等后端，不再是云 |
| `docs/24` 里 LoRA 标注「云 GPU 突发」 | LoRA 改为**本地夜间训练**，暂缓条件从「样本够就上云」改为「样本够就本地夜跑」 |
| `docs/23-预算`：云 GPU opex 是主要变量 | 云 GPU 月费大幅下降；单机**单点故障**风险上升，备份权重加大 |

### 8.2 新出现的核心问题：单卡竞争

Mac + 云时代不存在、现在必须解决的问题：

```text
单张 32GB 显卡 = 写作 / 视频 / TTS / LoRA 的共享瓶颈
        │
        ▼
必须新建：GPU 队列调度 + 模型常驻策略
（Redis/Celery 队列 + 显存预算表 + 单任务独占 + 失败降级重试）
```

这是过去多平台分摊算力时不需要的一层，现在是本地工厂的**新核心组件**。

### 8.3 RAM / NVMe 扩展解锁的能力

| 扩展 | 解锁的能力 |
|------|-----------|
| 64GB → 128GB+ RAM | 写作 LLM 常驻不卸载 + 视频模型换入缓冲 + CPU offload；可常驻 32B 写作模型 |
| 加装 NVMe #2 | 模型权重盘 / 视频 scratch 盘分离，视频批处理 IO 不再拖累系统盘 |
| 本地成为唯一生产中枢 | 灾备从「Mac 单点」变为「本工作站单点」，异地备份知识库 + LoRA + 案例库更关键 |

## 9. 一句话总结

**这台机器的平台（Core Ultra 9 285K + W880）和显卡（RTX 5090 32GB）都选对了，完全能支撑「每日 1 万字 + 每周 2 集 20 分钟动漫」的目标；现在要做的是把内存补到 128GB+、存储做好 NVMe 分层，然后用「白天写作、夜间跑视频、周末剪辑」的单卡队列工作流，把有限的 32GB 显存只花在 S/A 级动态镜头上——其余靠首尾帧、静态运镜、资产复用和后期完成。而硬件升级后，项目真正的功课是把「Mac + 云突发」的旧地基改写成「本地单卡 CUDA」，并补上单卡队列调度这一新核心组件。**
